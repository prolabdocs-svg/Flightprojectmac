# Phase 2B — Streaming Runtime (render + physics)

Converts the Phase 2A logical streamer (`src/world/master/masterStreaming.ts`) into real THREE.js geometry and Rapier
colliders, with `masterRuntime.ts` (`MasterTerrain`) kept as the single elevation authority. Nothing here generates
geography or duplicates height data — it only builds/tears down GPU and physics resources for the tiles the logical
streamer already decided on.

## New files

| File | Role |
|---|---|
| `src/world/master/renderStreaming.ts` | `MasterRenderStreamer` — THREE.js tile mesh lifecycle |
| `src/world/master/colliderStreaming.ts` | `MasterColliderStreamer` — Rapier heightfield collider lifecycle |
| `src/world/master/streamingRuntime.ts` | `MasterStreamingRuntime` — the single per-frame orchestrator |

`masterStreaming.ts`, `masterRuntime.ts`, `floatingOrigin.ts` are unchanged (Phase 2A logic and existing floating-origin
class reused as-is).

## Architecture

```
aircraft { x, z, vx, vz, aglM }
        │
        ▼
MasterStreamingRuntime.update()          ← the ONLY caller of MasterStreamer.update() (stateful, once/frame)
   1. origin.update(x, 0, z)             ← FloatingOrigin, x/z only (altitude never triggers a rebase)
   2. plan = streamer.update(view)       ← masterStreaming.ts: tiles, LOD, stitching, physics ring, prefetch
   3. render.applyPlan(plan)             ← MasterRenderStreamer: build/dispose meshes for plan.load / plan.unload
   4. colliders.apply(plan)              ← MasterColliderStreamer: colliders only for plan.tiles where physics=true
   5. if (delta) colliders.rebase(delta) ← shift every collider translation by the same delta FloatingOrigin applied
```

Render meshes are `THREE.Object3D`s registered with the shared `FloatingOrigin`, so a rebase moves them exactly like
every other registered object (`FloatingOrigin.update` already does this — no special-casing needed). Colliders are
not `Object3D`s, so `MasterColliderStreamer.rebase()` mirrors the same delta onto each Rapier collider's translation
directly; the heightfield data itself is never touched or regenerated by a rebase.

## Chunk lifecycle

1. `MasterStreamer.update()` returns `plan.load` (new tile ids, already capped by `maxLoadsPerUpdate`, prioritised
   physics > nearest) and `plan.unload` (ids no longer wanted).
2. `MasterRenderStreamer.applyPlan()` builds a `BufferGeometry` for every non-prefetch entry in `plan.load` — this set
   IS the per-frame budget; a tile becomes "resident" in the logical layer the moment it enters `load`, so deferring
   any of them would starve them forever (the streamer never re-offers an already-resident id). Vertices are stored in
   **tile-local** space (`0..size` on x/z); `mesh.position` carries the tile's local-frame offset, computed once via
   `origin.toLocal(...)`.
3. Separately, resident tiles whose `stitch` flags changed (a neighbour split or merged, changing which edges need
   T-junction correction) are rebuilt — capped by `MasterRenderStreamer.maxBuildsPerUpdate` (default 8), since the
   logical layer doesn't budget for those.
4. `plan.unload` disposes geometry, unregisters from `FloatingOrigin`, and removes the mesh from the scene.
5. `MasterColliderStreamer.apply()` creates a heightfield collider (via `RAPIER.ColliderDesc.heightfield`, same
   row/column-major conversion as the existing `terrainHeightfield.ts`) for every `plan.tiles` entry with
   `physics: true` — i.e. every L0 tile inside the physics ring — and removes any collider whose tile fell out of the
   ring or out of the plan entirely.

## LOD policy

Unchanged from Phase 2A (`masterStreaming.ts` `MasterStreamer.select`): 6 levels (L0 512 m / 16 m spacing → L5
16.4 km / 512 m spacing), 2:1-balanced quadtree, T-junction edge stitching so LOD boundaries are watertight without
skirts. Render streaming adds nothing sub-tile — near terrain gets fine L0/L1 geometry adequate for landing/low
flight, far terrain gets coarse L4/L5 for silhouette/continuity only, per the task's explicit Phase-3 boundary.

## Collider streaming policy

- Colliders exist **only** where `plan.tiles[i].physics === true` (L0 tiles inside `physicsRingM`, computed by
  `MasterStreamer.physicsRing`: `clamp(minRing, maxRing, baseRing + speed·secondsAhead)`, collapsing to just the
  tile(s) under the aircraft above `physicsAglCutoffM` — nothing can touch the ground, so no colliders are wasted).
- Height data comes from the same `HeightFn` (`MasterTerrain.groundAt`) as the renderer — no second elevation source,
  so collider and visual surface cannot diverge.
- High-speed safety: `physicsSecondsAhead` (14 s) and `physicsMaxRingM` (2500 m) already bound how far ahead the ring
  extends as speed grows; the stress test below exercises a 250–400 m/s sweep and the collider count still stays
  bounded (≤ 97 active in the worst sample; see baseline).
- No churn beyond what the ring boundary crossing requires: colliders are created/removed by tile id diff, never
  wholesale rebuilt.

## Floating-origin integration

- `MasterStreamingRuntime` owns one `FloatingOrigin(rebaseThresholdM=3072, gridSnapM=512)` (from
  `FLOATING_ORIGIN_CONFIG` in `masterStreaming.ts`), fed `(x, 0, z)` each frame — **altitude is deliberately excluded**
  from the rebase distance check so climbing to cruise altitude never forces a spurious rebase.
- World (master) coordinates ↔ render-local: `origin.toLocal/toGlobal`, used once per tile at build time; ↔ Rapier
  local: tracked in `MasterColliderStreamer`'s own `centersLocal` map, updated by `rebase()`.
- A rebase never changes the aircraft's true world position (untouched — floating origin only changes what "local"
  means for rendering/physics translation), and it snaps to the 512 m tile grid so tile vertex buffers never need
  recomputation after a rebase (Phase 2A's original justification for `gridSnapM`, verified still true since render
  meshes never touch their vertex data on rebase — only `mesh.position`).

## Frame budgets

- New tile builds: bounded by `MasterStreamer.maxLoadsPerUpdate` (constructor arg, default 12) — the logical layer's
  own per-frame cap, which the render adapter must fully honour (see Chunk lifecycle §2).
- Stitch-only rebuilds: `MasterRenderStreamer.maxBuildsPerUpdate` (default 8), independent budget.
- Collider add/remove: unbounded per frame today (colliders are ≤ ~90 in the worst observed case, cheap to
  create/remove relative to mesh builds) — flagged as Phase 3 debt below if profiling ever shows otherwise.

## Metrics exposed (devtools/inspection, not wired into production UI)

- `MasterRenderStreamer.metrics`: `activeTiles`, `pendingLoads`, `triangleCount`, `lastGenerateMs`, `lastUploadMs`.
- `MasterColliderStreamer.metrics`: `activeColliders`, `lastRebuildMs`.
- `MasterStreamingRuntime.metrics()`: combines both plus `distanceToUnpreparedM` — the guaranteed physics-ring radius
  (`plan.physicsRingM`), i.e. the minimum distance in any direction to terrain that isn't collider-backed, or
  `Infinity` above `physicsAglCutoffM` where nothing can touch the ground.

## Airfields

`MasterTerrain.airfields()` (existing, `src/world/airfields.ts` + `airfieldTerrain.ts`) already derives airfield
world position/elevation from the same `groundAt` the streaming tiles sample, so any airfield inside a loaded L0 tile
is elevation-consistent by construction — no new airfield database, no separate alignment step needed.

## Tests added

- `src/world/master/renderStreaming.test.ts` (6): load/no-load-for-prefetch, convergence, unload-on-move,
  per-frame load budget, L0 multiplicity (watertight prerequisite), dispose cleanup.
- `src/world/master/colliderStreaming.test.ts` (4): physics-only collider creation, removal on ring exit, bounded
  collider count under a high-speed sweep, `rebase()` translation correctness with unchanged collider count.
- `src/world/master/streamingRuntime.test.ts` (11 + 1 stress test): render/collider agreement, long multi-chunk
  flight bounded growth, low-altitude flight, high-speed ring widening, approach/landing coherence, teleport
  relocation, return-to-previous-area (no residual leak growth), multiple consecutive rebases (bounded local offset,
  no geographic jump), determinism, world-bounds sanity, and the required **headless stress test**.

All new/changed tests pass locally (`npx vitest run` → 733/733 passed, including the pre-existing suite).

## Stress test results (this run, `src/world/master/streamingRuntime.test.ts`, "stress test" describe block)

800 simulated frames along a gentle S-curve sweep (varying speed 50–250 m/s, altitude 50–350 m AGL), sampled every 20
frames (40 samples), forcing repeated load/unload and multiple floating-origin rebases:

```
steps: 800, samples: 40
maxTiles: 390          (cap is maxTiles=420 in DEFAULT_STREAM_CONFIG — never exceeded)
maxTriangles: 798,720
maxColliders: 97
final activeTiles: 137, pendingLoads: 7, triangleCount: 280,576
```

No-growth check: max tile/collider count in the second half of the run is required to stay within 1.3× (+ small
slack) of the first half's max — this passed, i.e. no monotonic growth in geometry or collider count over a long
route that revisits and departs many chunks.

## Visual runtime validation

**Not performed.** This environment has no way to attach a live 3D render + input loop for PROJECT FLIGHT's Electron/
Vite flight sim (no windowed GPU context available to this session), so takeoff → low flight → cruise → multi-tile
crossing → rebases → descent → landing could only be exercised headlessly (the stress test and scenario tests above
drive `MasterStreamingRuntime.update()` directly with synthetic flight paths and assert on tile/collider/geometry
state, never on rendered pixels). Popping, cracks, z-fighting, camera/velocity jumps, floating objects, and buried
airfields were **not** visually inspected. The headless coverage exercises the same code path
(`FlightScreen`/`WorldEnvironment` are not yet wired to this runtime — see Deferred/debt below), so a first real
integration pass in a browser/Electron session is the recommended next step before shipping.

## Performance instrumentation

`lastGenerateMs`/`lastUploadMs` (render) and `lastRebuildMs` (colliders) are wall-clock timers around each
`applyPlan`/`apply` call, explicit in the adapters themselves (no external profiler). No blind optimization was
applied; the stress test above is the reproducible baseline for future comparison. `lastUploadMs` currently mirrors
`lastGenerateMs` (THREE uploads lazily on next render, so there is no separate GPU-upload timer without a render call
in the loop) — a real GPU frame-time signal is Phase 3 debt once the runtime is wired into an actual render loop.

## Deferred / Phase 3 debt

- **Not wired into `FlightScreen`/`WorldEnvironment`/the Rapier world used in-game.** This phase builds and tests the
  adapters in isolation (as instructed — reuse the logical brain, build only the THREE/Rapier connectors); swapping
  the per-region `WorldEnvironment` terrain for `MasterStreamingRuntime` in the actual flight loop is a follow-up
  integration task, and is where real visual/physics validation (see above) must happen.
- No sub-tile detail, biomes, vegetation, cities, weather (explicitly out of scope, per the task).
- Collider add/remove has no explicit per-frame cap (unlike render); add one if profiling in real integration shows
  it matters (`ponytail:` — global per-apply loop today, cap similarly to `maxBuildsPerUpdate` if it ever shows up in
  a frame-time trace).
- `distanceToUnpreparedM` is derived from the configured physics ring guarantee, not a literal geometric raycast
  against the loaded footprint — correct as a lower bound given how `MasterStreamer` is built, but a tighter measure
  could be added if a future feature needs it.
